# Observability

Hapax exports OpenTelemetry metrics and traces. This document covers what is
instrumented, how to run it, and one measured result about label cardinality
that drove the design.

```bash
pip install 'hapax[otel,postgres]'
```

```python
from hapax import telemetry
from hapax.instrumented import InstrumentedTaskStore
from hapax.postgres import PostgresTaskStore

telemetry.configure(prometheus_port=9464)
store = InstrumentedTaskStore(PostgresTaskStore(conninfo))
```

Metrics are then at `http://localhost:9464/metrics`. With the extra not
installed, every call in `telemetry.py` becomes a no-op and the store behaves
exactly as before — the core package still has zero required dependencies.

## What is measured

| Metric | Type | Why it's here |
|---|---|---|
| `hapax.tasks.created` | counter | Arrival rate, split by whether an idempotency key was supplied |
| `hapax.tasks.claimed` | counter | Throughput |
| `hapax.tasks.recovered` | counter | **Claims of a task whose previous holder died.** See below |
| `hapax.tasks.transitions` | counter | State flow, labelled by destination state |
| `hapax.claim.duration` | histogram | Claim latency, including the miss case |
| `hapax.tasks.abandoned` | counter | Tasks past `max_attempts` |

`hapax.tasks.recovered` is the one worth explaining. Nothing in the system
reports a crash. A claim increments `attempts`, so any claim returning
`attempts > 1` means a previous holder took the task and never finished it —
its lease lapsed and this claim is the recovery. The absence of a heartbeat is
the detection, and this counter is that fact made visible.

Traces carry a span per operation, with `task_id` on the span. That is
deliberate, and it is the subject of the rest of this document.

## Design: a wrapper, not edits to the backend

`TaskStore` is a `typing.Protocol`, so conformance is structural. Instrumentation
is therefore a decorator — `InstrumentedTaskStore` — rather than metric calls
threaded through `postgres.py`:

- the durability logic stays readable, which is the part worth reviewing
- the backends stay dependency-free
- the same wrapper instruments `InMemoryTaskStore`, so the benchmark control
  group is measured by identical code

One gotcha found while building it. Forwarding via `__getattr__` is *not* enough
to satisfy the Protocol: a `runtime_checkable` `isinstance` check uses
`inspect.getattr_static`, which walks the class dictionary and deliberately
bypasses `__getattr__`. A method that exists only by forwarding is invisible to
it. Every contract method is therefore written out explicitly, even the ones
that only delegate — `tests/test_telemetry.py::test_the_wrapper_is_still_a_taskstore`
is the regression guard.

## Measured: what one high-cardinality label costs

`task_id` is the obvious thing to attach to a task metric. Every distinct
combination of metric name and attribute values is a separate time series, so
labelling by task id makes series count track task count — and task ids are
never reused, so it never stops growing.

`bench/cardinality.py` measures it instead of asserting it. Same workload, same
metrics, one flag flipped. Series counts and scrape sizes are exact; the
exposition is generated by the real Prometheus exporter into a private
`CollectorRegistry` per run.

```
   tasks  task_id label     series    scrape B  collect ms
------------------------------------------------------------
     100          False         22       3,286        1.07
     100           True        319      52,330        3.69
------------------------------------------------------------
    1000          False         22       3,304        0.42
    1000           True      3,019     496,945       39.47
------------------------------------------------------------
   10000          False         22       3,320        3.91
   10000           True     30,019   4,942,959      825.92
```

Without the label, **22 series regardless of workload** — 100 tasks and 10,000
tasks cost the same. With it, 3.0 series per task.

At 10,000 tasks:

- series: 22 → **30,019**
- scrape payload: 3,320 B → **4,942,959 B**, a **1,488×** increase
- collection: 3.91 ms → **825.92 ms**, a **211×** increase

The payload number is the one that matters operationally. That is transferred
every scrape interval, indefinitely, and 10,000 tasks is a small queue.

So `task_id` is dropped from metric attributes by default. `telemetry.attrs()`
enforces it in one place, and the flag exists only so the failure can be
reproduced. The identifier still exists on spans, where it is free: a trace is
retrieved by id rather than aggregated across, so a unique attribute costs one
span rather than one time series.

```bash
python bench/cardinality.py --sizes 100,1000,10000 --json bench/cardinality_results.json
```

## A note on running this alongside the tests

`bench/cardinality.py` at 10,000 tasks is heavy enough to disturb its
neighbours. Running it in the same shell invocation as the suite made
`test_two_workers_race_same_task_charge_once` and
`test_a_killed_worker_is_recovered_without_anyone_asking` fail, and the suite
took 279 s instead of 5.5 s. Both pass in isolation, and the full suite passes
on its own (114 tests, 5.53 s).

Those two tests assert on crash-recovery and race timing, so they are sensitive
to machine load by nature. Run the benchmark separately from the suite.
